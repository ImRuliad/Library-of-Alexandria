## ***2.2 Interface***
---
*GFS provides a familiar filesystem interface, but it does not implement a standard API like POSIX*

- Files are organized hierarchically in directories and identified by pathnames
- Supports Create, Delete, Open, Close, Read, and Write Operations.
- Has *snapshot* and *record append* operations
- *Record append* allows multiple clients to append data to the same file concurrently while guaranteeing *atomicity*
- Useful for implementing multi-way merge results and producer-consumer queues that many clients can simultaneously append to without *locking*

## ***2.3 Architecture***
---
*A GFS cluster consists of one single master and multiple chunkservers and is accessed by multiple clients.*

![[Screenshot 2026-10-21 at 6.49.15 PM.png]]


- Each *chunkserver* runs on a commodity Linux machine running a user-level server process.
- You can run both a *chunkserver* and a client on the same machine as long as machine resources permit.
- Files are divided into fixed-sized chunks. Each chunk is identified by an immutable and globally unique 64-bit *chunk handle* assigned by the master at the time of chunk creation.
- Chunkservers store chunks on local disks as Linux files and read or write chunk data specified by a chunk handle and byte range.
- For reliability, each chunk is replicated on multiple chunkservers. By default, three replicas are stored, but users can designate different replication levels for different regions of the file namespace.

- The master contains all filesystem metadata (includes namespace, access control info, mapping from files to chunks, current location of chunks)
- Controls system-wide activities such as chunk lease management, garbage collection of orphaned chunks, chunk migration between chunkservers.
- Master periodically communicates with each chunkserver in *HeartBeat* messages to give it instructions and collect its state.

- GFS client code linked into each application implements the filesystem API and communicates with the master and chunkserver to read or write data on behalf of the application.
- Clients interact with maser for metadata operations
- All data-bearing communication goes directly to the chunkservers
- No POSIX API therefore, no Linux vnode layer

- Neither the client nor chunkserver caches file data
- Client caches offer little benefit because most apps stream through huge files or have working sets too large to be cached
- Not having caches simplifies the client and system by eliminating cache coherence issues (Clients do cache metadata, however)
- Chunkservers need not to cache file data because chunks are stored as local files and Linux's buffer cache already keeps frequently accessed data in memory

## ***2.4 Single Master***
---
*Having a single master vastly simplifies the design and enables the master to make complex chunk placement and replication decisions using global knowledge*

- Read and Writes must be minimized to limit the bottleneck
- Clients never read and write file data through the master, client instead asks the master which chunkservers it should contact
- The above info is cached for a limited time and interacts with the chunkservers directly for many subsequent operations

#### **What happens in a simple read?**
1. Used fixes size chunk size, the client translates the file name and byte offset specified by the application into a chunk index within the file
2. Sends the maser a request containing the file name and chunk index
3. Master replies with corresponding chunk handle and locations of the replicas
4. Client caches this information using the file name and chunk index as the key
5. Client sends a request to one of the replicas (most likely the closest one)
6. Request specifies the chunk handle and a byte range within that chunk
7. Further reads of the same chunk require no more client-master interaction until cached info expires or the file is reopened

## ***2.5 Chunk Size***
---
*Chunk size is one of the key design parameters, 64 MB is used as the chunk size, which is larger than typical file system block sizes.*

- Each chunk replica is stored as a plain linux file on a chunkserver and is extended only as needed.
- Lazy space allocation avoids wasting space due to internal fragmentation, perhaps the greatest objection against such a large chunk size.

A large chunk size offer several important advantages
- It reduces clients' need to interact with the master because reads and writes on the same chunk require only one initial request to the master for chunk location information.
- This reduction is important because applications mostly read and write large files sequentially.
- Even for small random reads, client can comfortably cache all chunk location information for a multi-TB working set.
- A client is more likely to perform many operations on a singe large chunk, reducing network overhead by keeping a persistent TCP connection to the chunkserver.
- Reduces the size of the metadata stored on the master
- Allows for the metadata to be kept in memory

A large chunk size also has its disadvantages
- A small file consists of a small number of chunks
- Chunkservers may become hotspots if many clients are accessing the same file
- Hotspots did develop when GFS was first used by a batch-queue system: an executable was written to GFS as a single-chunk file and then started on hundreds of machines at the same time.
- The few chunkservers storing this executable were overloaded by hundreds of simultaneous requests.
- The above was fixed by storing such executables with a higher replication factor and making the batch-queue system stagger application start times.
